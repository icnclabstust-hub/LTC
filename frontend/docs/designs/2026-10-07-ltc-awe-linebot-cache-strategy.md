## 1. 前提

- 會議已定案：快取改在後端處理，**前端不加輕量資料庫，簡報 F3 手機端 SQLite 佇列作廢**（議題九）。LINE 本身沒有可存狀態的前端，所有狀態都在地端後端。
- 一次請求的路徑（附錄一）：①音檔下載 → ②語音轉文字與語者分離 → ③關鍵字／意圖路由 → ④檢索 → ⑤生成 → ⑥LINE 回覆。
- ②的耗時與音檔長度成正比，**快取無法縮短**（附錄一）。已知數據：71.8 秒音檔切句＋轉文字約 4.0～4.6 秒（RTF ≈ 0.06，筆電 CPU）；LINE 單則語音可錄 15 分鐘以上。
- 回應時效：LINE 收到訊息至回覆送達 LINE，P95 ≤ 3 秒（議題二）。
- 快取單位：會後補充暫定為「對話 block」（議題九），對應定義文件的「輪」。

## 2. 要回答的問題

1. 語音處理段要交給後端的單位是什麼（整則訊息或一輪）？這決定前後端怎麼銜接。
2. 語音處理段本身需要哪些快取？
3. 失效規則是什麼？

## 3. 方案比較：交給後端的單位

| | 方案 A：整則語音處理完才交 | 方案 B：每結束一輪就交（選定） |
|---|---|---|
| 做法 | 一則語音全部切句、轉文字、切輪、判意圖後，一次送出 | 依時間順序處理，某一輪結束（3 秒靜音或下一個喚醒詞）就先把該輪紀錄送給後端，其餘繼續處理 |
| 延遲 | 等全部處理完；10 分鐘語音光轉文字約 36 秒 | 第一輪結束即可開始檢索與生成，與後段轉文字平行 |
| 與快取的關係 | 後端只能以「整則訊息」為鍵 | 後端可直接以「輪」為快取單位，符合議題九會後補充 |
| 缺點 | 長語音必然超過 3 秒 | 一則訊息會產生多次送出，後端要以 `turn_id` 去重；跨訊息未結束的輪要等下一則 |

**選定方案 B**。理由：長語音下只有 B 有機會讓第一個答案在合理時間內出現，也讓「輪」成為前後端共用的快取單位。

## 4. 預取規則：何時先送請求給後端

會議中老師指出關鍵問題是「先丟出請求，還是等使用者問完再丟」（議題九）。第 3 節決定了「最晚」在一輪結束時交出；本節決定「能不能更早」。

| | 方案 P0：輪結束才送 | 方案 P1：意圖信心達門檻即預取（選定，提案學生提出） | 方案 P2：每句都送 |
|---|---|---|---|
| 做法 | 只在輪結束時送一次 | 輪進行中，某句的意圖屬於「需要後端回答的類別」且信心 ≥ 門檻，就先送出暫定請求；輪結束時再送最終紀錄 | 每切出一句就送 |
| 延遲 | 最慢 | 檢索與生成可與後續語句的轉文字平行 | 最快 |
| 浪費 | 無 | 意圖判錯或後續語句改變意圖時，預取結果作廢 | 大量無效請求，與即時請求爭搶地端運算資源（附錄一（7）的風險） |

**選定 P1**。對應附錄一：P1 即（7）block 預取的後半段「長音檔可於轉文字進行中先以部分文字啟動檢索」——輪尚未結束，就以已轉出的語句先啟動檢索；（7）的前半段「回答完一個 block 後預先計算常見後續問題」不採用。附錄一要求（7）「待多輪定義追認後再做，且僅於閒置時執行」，本設計於 10/12 追認多輪定義，且預取只在閒置時執行（見下）。另以（3）對話狀態快取配合多人多輪（第 5 節 C3、C4）。

P1 加上兩個條件：

1. **只有需要後端回答的意圖才觸發預取**：規範詢問、服務請求、身體不適陳述（擴大為身體狀況陳述或詢問）。確認或同意、情緒安撫或閒聊、資訊告知或交接、拒絕或抗拒，不需要檢索或生成，不觸發預取，只隨輪結束送出。觸發類別清單待老師確認。
2. **門檻要用資料定，不能先假設**：以交叉驗證各折測試集的預測信心，找出「信心 ≥ 門檻時判對的比例（precision）≥ 目標值」的最低門檻，並同時報告會觸發預取的比例（coverage）。意圖模型已改為 BERT（`hfl/chinese-roberta-wwm-ext`、繁體原文，交叉驗證準確率 0.903，見 `2026-10-09-ltc-intent-bert-spike.md`）；BERT 的信心分數常偏高，判錯的句子也可能很高，所以門檻要以該模型交叉驗證測試折的預測信心實際量測，不直接沿用 0.8 之類的固定值。

預取流程：

```
輪進行中，每切出一句 u：
    (intent, conf) ← 意圖模型(u)
    if intent ∈ 觸發類別 and conf ≥ 門檻 and 本輪尚未對同一意圖預取：
        送出暫定請求 { turn_id, utterance_id, 文字, intent, conf, provisional: true }
輪結束：
    送出最終輪次紀錄 { turn_id, ..., provisional: false }
後端：
    最終紀錄的意圖與預取時相同 → 直接使用預取的檢索／生成結果
    不同 → 作廢預取結果，依最終紀錄重做
```

- 預取請求以 `turn_id＋utterance_id` 為冪等鍵，同一句不重送。
- 預取只在地端有閒置運算資源時執行；即時請求優先（附錄一（7））。
- 驗收：命中率（預取結果被最終採用的比例）、命中時與未命中時的延遲、因預取作廢而浪費的請求數，對應附錄一第五點的四個數字。

## 5. 語音處理段的快取與狀態

| # | 項目 | 鍵 | 內容 | 存放／存活時間 | 省下什麼 | 對應附錄一 |
|---|---|---|---|---|---|---|
| C1 | 模型常駐 | — | VAD、ASR、喚醒詞、聲紋、意圖模型於服務啟動時載入，常駐記憶體 | 行程記憶體／服務存活期間 | 每次請求的模型載入時間（實測 1.4～2.1 秒） | — |

不採用：
- **語音或逐字稿的語意快取**：口語語音幾乎不會重複，命中率可預期極低；且附錄一已判定語意快取風險最高。
- **前端輕量資料庫**：會議已決議不採。

## 6. 對前後端銜接的影響（交件重點）

1. **銜接單位改為「輪」，並加上預取**：符合條件時先送暫定請求（第 4 節），輪結束再送最終紀錄。語音處理段每結束一輪，送出一筆輪次紀錄（含所屬語句與意圖，欄位見定義文件 3.3、4.3、5.3）。後端以 `turn_id` 為冪等鍵。
2. **後端的快取鍵可沿用輪的內容**：附錄一的（1）關鍵字預審答案表、（2）精確比對，鍵可由「輪內正規化後的語句＋意圖類別＋知識庫版本」組成；這部分由後端組設計，語音處理段只負責提供正規化文字與意圖。
3. **狀態都在後端**：LINE 端不存任何狀態；身分聲紋與進行中的輪放在 C3、C4。
4. **回覆時效（簡報 L2）**：方案 B 讓第一輪的答案可能在 1 分鐘回覆權杖時效內送出；超時的部分才改主動推送。細節另見 L2 補件。

## 7. 失效原則

- C2：存活 24 小時後到期；同一 `messageId`（聊天室）或同一 `session_id`＋片段序號（網頁錄音）再次出現時，直接回傳快取結果。
- C3：照護員停止錄音（或網頁斷線逾時）時清除；清除前把 `open` 的輪以 `session_stop` 原因結束並送出，避免遺失。
- C4：照護員重新設定某身分時覆寫；照護員刪除住民或聲紋時一併刪除（生物特徵資料）。
- 後端快取（附錄一）：一律以 PostgreSQL 的文件版本為鍵的一部分，知識庫更新即整批作廢（附錄一第四點），本段不另訂。

## 8. 驗收量測（對應待辦 12，期限 10/19）

- 分段記錄①下載、②切句＋轉文字＋語者辨識、輪次切分、意圖判定的耗時，報告 P50／P95，並註明音檔長度與硬體。
- 方案 B 的效益：量測「訊息送達」到「第一輪紀錄送出」的時間，與「整則處理完」的時間比較。
- C2：以重送同一事件驗證不重複處理、不重複送出。
- C3：跨兩則訊息的輪能正確接續；閒置到期後狀態清除。
