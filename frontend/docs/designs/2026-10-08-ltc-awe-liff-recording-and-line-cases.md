## 1. 背景與問題

需求釐清（GD 步驟 1，2026-10-08 與提案學生確認）：

- 要解決什麼問題：照護員在住宿式機構照護住民時雙手忙碌，需要不必動手就能記錄多人對話、即時得到法規答案；書面提問要能轉給督導回覆；每天的工作狀況要能用口述回報。
- 誰會用：照護員（LINE 聊天室與 LIFF 網頁）；督導（主管）在本網頁的督導頁面回覆轉人工的請求；管理員發放綁定碼。開發與測試階段只有提案學生本人與同學。
- 不做會怎樣：照護員只能事後憑記憶記錄、自己查法規或另外打電話問督導；多人、多輪、多意圖的研究沒有可用的收音入口。

現況調查（GD 步驟 2）的結論：切句、轉文字、喚醒詞、聲紋、意圖、後端介面都有既有實作或設計可沿用（第 3 節）；缺的是 LIFF 網頁、聊天室選單、網頁錄音分段上傳、文字訊息 webhook。

收音實測（2026-10-09，提案學生，Samsung Galaxy Note 10 Lite，以老師網頁測試）：

| 開啟方式 | 麥克風 | 離開網頁（切到其他 App） | 關閉螢幕 |
|---|---|---|---|
| LINE 內建瀏覽器 | ❌ permission denied | — | — |
| 外部瀏覽器 | ✅ 可錄音 | ✅ 持續正常錄音 | ⚠️ 斷斷續續，出現漏聽與轉文字幻聽 |

因此錄音頁一律以外部瀏覽器開啟，錄音中須保持螢幕亮著（第 5.1 節）。

## 2. 目標與非目標

### 2.1 功能需求

**平台**：只支援 Android（實測機型 Galaxy Note 10 Lite）；iOS 不在本次範圍。

**場景**：以住宿式長照機構為主（對應後端知識庫：機構相關法規、機構內規、作業程序）；居家服務不在本次範圍。

**身分與綁定**

| 身分 | 怎麼取得 | 能做的事 |
|---|---|---|
| 管理員 | LINE `userId` 寫在 `.env`（`LINE_ADMIN_USER_IDS`） | 新增照護員、督導帳號並產生綁定碼；查看綁定狀態；停用帳號 |
| 照護員 | 加 Bot 好友後輸入管理員發的綁定碼 | 錄音模式、LINE 案件、今日狀況回報 |
| 督導（主管） | 同上 | 督導頁面：查看並回覆照護員的轉人工請求 |

1. 管理員在網頁上新增帳號（姓名、身分），系統產生一次性綁定碼；管理員把綁定碼交給本人。
2. 使用者第一次加 Bot 好友時，Bot 回覆歡迎訊息與「輸入綁定碼」按鈕，開啟 LIFF 綁定頁；輸入正確的綁定碼後，該 LINE `userId` 與帳號、身分綁定，綁定碼即失效。
3. 未綁定的使用者：Bot 只提示綁定，聊天室文字一律不處理；網頁只能進綁定頁。
4. 綁定後依身分切換聊天室底部選單（per-user Rich Menu）與網頁可見的分頁。
5. 網頁右上角顯示自己的名字，點擊後出現下拉選單。管理員（`.env` 指定的 `userId`）的下拉選單有「切換身分」，可隨時在管理員、督導、照護員之間切換；網頁記住上次使用的身分。照護員與督導只有自己的一種身分，不顯示切換。
6. 身分檢查一律在伺服器端：每個 API 先以 LIFF ID token 驗證 `userId`，再檢查「目前使用的身分」是否有權限；只有管理員帳號能宣告其他身分。

**督導頁面**

1. 所有督導共用一個待處理清單；不論照護員對應一位或多位督導，請求都進同一個清單。
2. 每筆請求顯示：發送的照護員、來源（錄音模式的某一輪或 LINE 案件）、問題內容、轉人工原因、時間。
3. 每筆請求下方有輸入框與「發送」按鈕；送出後，回覆存入該筆紀錄，並傳回給照護員（LINE 推送＋更新語音紀錄或 LINE 案件）。
4. 已回覆的請求標示回覆的督導與時間，移到「已回覆」。

**入口**：LINE 聊天室底部選單（Rich Menu）放「錄音模式」「今日狀況回報」「使用說明」，按下開啟 LIFF 網頁對應分頁。LIFF 網頁有三個分頁：錄音模式、LINE 案件、今日狀況回報。需要麥克風的頁面（錄音模式、今日狀況回報）以 `liff.openWindow({ external: true })` 在外部瀏覽器開啟。

**路線 1：錄音模式**

1. 開始前先選「現在照護哪一位住民」。住民清單以「照護員 × 住民」為單位，可刪除；名稱一律用代稱（例：「住民 A」），網頁提示不得輸入姓名、房號或其他可辨識身分的資訊（長期照顧服務法第 43 條）。來探視的家屬，聲紋也歸在該住民底下。
2. 錄音同意（長期照顧服務法第 43 條：錄音須經住民書面同意；無法表示意思者，須經法定代理人或主要照顧之最近親屬書面同意）：
   - 住民入住時由機構取得書面同意書；系統在住民資料記錄「已有書面同意（日期）」。**只有已記錄書面同意的住民才能開始錄音。**
   - 每次錄音前，照護員再確認一次在場者同意，按「確認錄音」才開始。
   - 在場的家屬或照護員不同意錄音時，改用**手動打字提問**：照護員輸入問題，送給後端回答或轉督導；回答與督導回覆顯示在該筆紀錄最上方。
3. 錄音持續進行，以「輪」切分：
   - 輪的開始：照護員說「小照你好」。
   - 輪的結束（任一成立）：照護員說「小照請回答」；靜音 3 秒；照護員說下一個「小照你好」（同時開始新的一輪）。
   - 「小照你好」「小照請回答」不轉文字、不判斷意圖。
   - 輪外的語音不保存。KWS 漏抓喚醒詞時，輪外片段**只轉開頭 2 秒**比對「小照你好」，比對完即丟、不保存（2026-10-13 起，`2026-10-13-ltc-awe-wake-word-miss-spike.md`）。
4. 說話者身分：
   - 某住民第一次錄音時，先告知聲紋相關規定並徵詢在場者是否同意儲存聲紋。
   - **同意**：照護員在第一輪逐句設定說話者身分，系統儲存各人的聲紋；之後的輪次自動辨識，只有出現未記錄的聲音時才請照護員設定。
   - **不同意**：不儲存聲紋，每一輪都由照護員逐句選擇身分。
5. 輪進行中持續判斷每句的意圖與關鍵字；信心達門檻就把請求送給後端，由後端決定直接回答或轉人工（第 5.3 節）。
6. 本輪結束後：後端回傳的回答顯示在該輪語音紀錄的最上方；並以語音播放，播放期間關閉麥克風（TTS 與瀏覽器自動播放限制列為待辦）。
7. 每一輪存成一筆「語音紀錄」，列在錄音模式分頁下方；點進去顯示逐字稿、每句的說話者與意圖、後端回答。

**路線 2：LINE 案件**

1. 聊天室只處理以「小照你好」開頭的**文字**訊息（例：「小照你好，家屬要我幫忙代購，機構規定可以嗎？」）；其他訊息一律不回應，使用說明放在選單內。
2. 收到後建立一筆「LINE 案件」，把問句送給後端。
3. 後端判斷：只回答規範查詢並附出處（依後端知識庫，以住宿式機構的法規、機構內規、作業程序為主）；醫療、用藥、補助金額，以及知識庫沒有依據的問題，一律轉人工，進入督導頁面的待處理清單，由督導回覆。
4. Bot 取得回答或督導回覆後傳回聊天室，並存在該筆 LINE 案件下方。

**今日狀況回報**

1. 照護員以語音講述當天狀況（照護了哪些住民、各住民的狀況，以代稱描述），轉成逐字稿。
2. 只有照護員本人說話，不徵詢同意、不判斷意圖、不做語者辨識。
3. 逐字稿標示當天日期與照護員，送到督導頁面供督導確認；保存 24 小時後刪除。

**資料保存**

| 資料 | 保存 | 理由／備註 |
|---|---|---|
| 語音紀錄、LINE 案件（本機） | 1 天 | 對應照護員當日工作狀況 |
| 聲紋（照護員 × 住民） | 永久，直到照護員刪除 | 須告知相關規定；不再照護該住民時由照護員自行刪除；網頁提供編輯、刪除按鈕 |
| 同意紀錄 | 存在後端資料庫 | 由後端組管理 |
| 轉人工紀錄 | 後端資料庫只記錄照護員的問題 | 督導的回覆不送後端，只存在本服務 |
| 今日狀況回報 | 24 小時 | 標示當天日期，供督導確認後刪除 |
| 督導請求（問題＋回覆） | 未回覆前一直保留；回覆後 1 天 | 不受原語音紀錄、LINE 案件 1 天期限影響 |
| 帳號、身分、綁定 | 永久，直到管理員停用 | 綁定碼一次性 |
| 原始錄音 | 轉成文字後立即刪除 | 只保存逐字稿（含每句說話者身分），存入語音紀錄 |

### 2.2 非目標（本次不做）

- 不處理 LINE 聊天室的語音訊息、圖片、群組聊天。
- 不實作後端的回答生成、知識庫、轉人工判斷（後端組負責）；不使用 Open WebUI。
- 管理員不提供從網頁啟動或關閉服務（服務的啟停在提案學生筆電上操作）。
- TTS 元件選型與手機瀏覽器自動播放限制：列待辦，不在本次範圍。
- 不部署到共用機器、不排程；只在測試時於提案學生筆電手動啟動。
- 不錄真實照護現場；只用提案學生本人與同學的模擬對話。
- 意圖模型換模型：待老師決定，本次沿用 care7 AWE（準確率約 0.48）。

## 4. 方案比較

兩案差在「喚醒詞與切輪在哪裡偵測」，這決定音訊要不要一直送到伺服器。

| | 方案 A：伺服器端偵測（選定） | 方案 B：瀏覽器端偵測 |
|---|---|---|
| 做法概述 | 網頁錄音後，每 0.5～1 秒上傳一個音訊片段到地端伺服器；伺服器以 sherpa-onnx KWS 偵測兩個關鍵詞、VAD 判斷靜音 3 秒並切輪，同時切句、轉文字、比對聲紋、判斷意圖 | 網頁用瀏覽器內建的語音辨識（Web Speech API）偵測「小照你好」，聽到才開始上傳；切輪也在瀏覽器判斷 |
| 優點 | 所有音訊只送地端伺服器，不經第三方語音服務；KWS 模型與自訂關鍵詞已驗證可行；與既有 Python 處理鏈相同語言 | 伺服器只收到有喚醒詞的片段，流量小；網頁端即時回饋 |
| 缺點／風險 | 錄音期間持續上傳，需穩定網路；伺服器要為每個錄音 session 維持串流狀態；地端算力要能同時處理多人 | Web Speech API 在 Chrome、Safari 會把語音送到 Google／Apple 處理，等於音訊離開地端；LINE 內建瀏覽器多半不支援；中文喚醒詞準確度不可控 |
| 成本 | 伺服器端串流處理需新寫（約 2～3 個工作天） | 網頁端較簡單，但不支援時無備案 |

**選定方案 A**（2026-10-09 提案學生確認）。理由：本研究的主軸是地端處理，方案 B 會把現場語音送到第三方；方案 A 的關鍵元件都已有 spike 驗證。

收音位置（兩案共通）：LINE 內建瀏覽器實測無法使用麥克風，錄音頁一律以 `liff.openWindow({ external: true })` 在外部瀏覽器開啟。

## 5. 系統設計

### 5.1 資料流

錄音頁在外部瀏覽器開啟後，以 Screen Wake Lock API 要求螢幕保持亮著，並提示「錄音中請勿關閉螢幕」；切到其他 App 時可持續錄音（實測），螢幕關閉時暫停判定並在恢復後提示可能有漏聽。外部瀏覽器沒有 LINE 登入狀態，需在外部瀏覽器內再走一次 LINE Login（LIFF SDK 支援）。

```
路線 1  外部瀏覽器錄音頁 ─(HTTPS, 音訊片段)→ 地端服務
          串流：KWS（小照你好／小照請回答）＋ VAD（3 秒靜音）→ 切輪
          每句：Paraformer 轉文字 → 聲紋比對（有同意時）→ 意圖（AWE；BERT 比較 spike 進行中）
          意圖／關鍵字信心 ≥ 門檻 → POST 後端（provisional）→ 回答暫存
          輪結束 → 送最終輪次紀錄 → 回答置頂顯示、語音播放（播放時暫停收音）
路線 2  LINE 聊天室文字「小照你好…」→ webhook（驗簽、去重）→ 建 LINE 案件
          → POST 後端 → 回答（附出處）→ reply（1 分鐘內）或 push → 存入案件
轉人工  後端回覆 awaiting_human → 本服務建立督導請求 → 督導頁面待處理清單
          → 督導輸入回覆並發送 → 存入請求（不送後端）→ push 給照護員
          → 更新對應的語音紀錄（置頂）或 LINE 案件
回報    外部瀏覽器回報頁錄音 → 上傳 → 轉文字 → 標示日期 → 顯示在督導頁面 → 24 小時後刪除
綁定    加好友（follow）→ 歡迎訊息＋「輸入綁定碼」→ LIFF 綁定頁 → 驗證綁定碼
          → 綁定 userId、身分 → 切換該使用者的 Rich Menu
```

### 5.2 對外介面（草稿，示意用）

本服務提供給 LIFF 網頁（以 LIFF ID token 驗證身分，由伺服器向 LINE 驗證）：

| 方法與路徑 | 用途 |
|---|---|
| `GET/POST/PATCH/DELETE /api/residents` | 住民（照護員 × 住民）的列表、新增、改名、刪除 |
| `PATCH /api/residents/{id}/written-consent` | 記錄住民書面同意的日期（無此紀錄不能錄音） |
| `POST /api/residents/{id}/voiceprint-consent` | 記錄聲紋同意或不同意 |
| `POST /api/residents/{id}/text-questions` | 手動打字提問（不錄音時），送後端回答或轉督導 |
| `DELETE /api/residents/{id}/voiceprints` | 刪除該住民全部聲紋 |
| `POST /api/sessions` | 開始錄音（帶 `resident_id`、`consent_confirmed: true`），回傳 `session_id` |
| `POST /api/sessions/{id}/chunks` | 上傳音訊片段（帶序號，冪等） |
| `POST /api/sessions/{id}/stop` | 停止錄音 |
| `GET /api/sessions/{id}/turns` | 取得各輪紀錄（逐字稿、說話者、意圖、回答） |
| `PATCH /api/turns/{id}/utterances/{idx}/speaker` | 設定或修正某句的說話者 |
| `GET /api/line-cases` | LINE 案件列表與回覆 |
| `POST /api/daily-reports` | 上傳今日狀況回報音訊 |
| `POST /api/bind` | 以綁定碼綁定目前的 LINE `userId`（未綁定者可用） |
| `GET/POST/PATCH /api/admin/accounts` | 管理員：帳號列表、新增（回傳一次性綁定碼）、停用 |
| `POST /api/admin/accounts/{id}/binding-code` | 管理員：重新產生綁定碼 |
| `GET /api/supervisor/requests` | 督導：待處理／已回覆清單（含照護員姓名、來源） |

每個 API 標註允許的身分；照護員 API 只回傳本人資料。

本服務呼叫後端（沿用 v2.2，細節待與後端組確認）：`POST /v1/query`（問句或輪內預取，帶 `provisional`）、`POST /v1/scene`（整輪紀錄）、查詢請求狀態（含 `awaiting_human`／`human_answered`）；今日回報端點待後端組提供。

### 5.3 預取與回答

- 觸發：句子意圖屬於觸發類別，或命中關鍵字，且信心 ≥ 門檻。觸發類別與門檻沿用 cache-strategy v0.2 第 4 節，待老師確認。
- 是否回答、是否轉人工一律由後端判斷；本服務不自行過濾。
- 後端回答先暫存於該輪；輪結束時若最終意圖與預取時不同，以最終紀錄重送，舊結果作廢。
- 轉人工時，該輪紀錄顯示「已轉督導」，督導回覆後更新到紀錄最上方。

### 5.4 資料模型（草稿）

```
accounts       (id, display_name, role: caregiver|supervisor, line_user_id, status: pending|active|disabled, created_at)
binding_codes  (code_hash, account_id, expires_at, used_at)
supervisor_requests (id, caregiver_account_id, source: turn|line_case, source_id, question, reason,
                     status: open|replied, reply, replied_by, replied_at, backend_request_id)
daily_reports  (id, caregiver_account_id, report_date, transcript, created_at)   -- 24 小時後刪除
residents      (id, caregiver_line_user_id, alias, written_consent_date, created_at)   -- alias 為代稱，不存姓名、房號
text_questions (id, resident_id, question, answer, status, created_at)   -- 1 天後刪除
voice_consents (resident_id, decision: agreed|declined, decided_at)    -- 正式紀錄另送後端資料庫
voiceprints    (id, resident_id, person_label, role, embedding, created_at, updated_at)
sessions       (id, resident_id, started_at, ended_at, consent_confirmed_at)
turns          (id, session_id, seq, started_at, ended_at, end_reason, answer, answer_status)
utterances     (turn_id, idx, start_ms, end_ms, text, speaker_role, speaker_source: voiceprint|manual, intent, intent_conf)
line_cases     (id, line_message_id, caregiver_line_user_id, question, answer, status, created_at)
latency_logs   (session_id, utterance_seq, upload_ms, kws_ms, vad_ms, asr_ms, speaker_ms, intent_ms,
                request_build_ms, backend_ms, created_at)   -- 只存數字，不存文字與音訊
```

- `end_reason`：`answer_keyword`（小照請回答）、`silence`、`next_wake_word`、`session_stop`。
- `role`：照護員／家屬／長輩／督導／其他工作人員（護理師、同事等）／未辨識。「未辨識」只用於偵測到新加入、聲紋比對不到且尚未由照護員設定身分的人；設定後改為該身分。
- turns、utterances、line_cases 存活 1 天後刪除；voiceprints 永久，隨住民刪除一併刪除。

### 5.5 錯誤處理與日誌

- 音訊片段帶序號，伺服器以 `session_id＋序號` 去重；斷線後網頁重送未確認的片段。
- webhook 驗證 `X-Line-Signature`，以 `webhookEventId` 去重。
- 回覆權杖逾 1 分鐘改用 push；push 失敗記錄錯誤並在 LINE 案件標示「通知失敗」。
- 日誌只記 id、耗時、狀態碼，不記逐字稿與音訊內容。
- 分段記錄耗時（對應待辦 12），計時點與 `2026-10-09-ltc-intent-bert-spike.md` 第 5.5 節一致：

  | 代號 | 計時點 | 相減得到的延遲 |
  |---|---|---|
  | P0 | 伺服器收到音訊片段 | — |
  | P1 | 關鍵詞偵測完成（小照你好／小照請回答） | P1−P0：KWS |
  | P2 | VAD 切出一句 | P2−P1：VAD |
  | P3 | Paraformer 轉文字完成 | P3−P2：ASR |
  | P4 | 聲紋比對完成（未同意聲紋時略過，記為空值） | P4−P3：聲紋 |
  | P5 | 意圖判斷完成 | P5−P4：意圖（內部再拆 I1～I4，見 spike 文件） |
  | P6 | 送出後端請求 | P6−P5：組請求 |
  | P7 | 收到後端回覆 | P7−P6：後端往返 |

  另記網頁端「片段錄完」到 P0 的上傳時間（網頁送出時附上客戶端時間戳；手機與伺服器時鐘可能不同步，此段只作參考）。每句寫一筆 `latency_logs`（見 5.4），報表以 P50／P95 呈現各段。計時用伺服器單調時鐘（`time.perf_counter()`），GPU 推論量測前後同步，避免低估。

## 6. 安全與隱私考量

- **生物特徵**：聲紋屬個人資料保護法的特種個資範疇（待老師與機構確認適用）；儲存前須告知用途、保存期限、刪除方式並取得同意；不同意不儲存；照護員可隨時刪除。告知文字請老師審閱。
- **錄音同意**：依長期照顧服務法第 43 條，住民須有書面同意（入住時由機構取得，系統記錄日期）才能錄音；每次錄音前照護員再確認；在場者不同意時改用手動打字提問。
- **去識別**：住民、家屬一律以代稱記錄，不輸入姓名、房號等可辨識身分的資訊。
- **存取控制**：LIFF 以 ID token 由伺服器向 LINE 驗證；身分權限一律在伺服器端檢查。照護員只能看到自己的住民、語音紀錄與案件；督導看得到所有照護員送出的請求與今日回報，但看不到聲紋與未送出的語音紀錄；管理員只管理帳號，不看照護內容。
- **綁定碼**：一次性、有效期限、只存雜湊值；管理員 `userId` 只放 `.env`。
- **傳輸**：全程 HTTPS（ngrok 固定網域）；音訊只送到地端伺服器，轉成文字後即刪除；後端只收到文字與意圖，不送第三方語音服務。
- **金鑰**：channel secret、access token 只放 `.env`，不進版控。
- **測試資料**：只用本人與同學的模擬對話。

## 7. 測試策略

- **單元**：切輪狀態機（三種結束條件、喚醒詞不轉文字）、片段去重、資料保存期限清除、聲紋同意分支。
- **整合**：以錄好的模擬對話音檔模擬分段上傳，檢查輪數、每句說話者、意圖與預取請求；以 LINE 模擬事件測試 webhook 驗簽、去重、前綴過濾。
- **單元（權限）**：每個 API 以三種身分與未綁定者各呼叫一次，確認只有允許的身分能存取；綁定碼重複使用、過期、錯誤時拒絕。
- **實機**：Galaxy Note 10 Lite，外部瀏覽器測錄音、切換 App 持續錄音、Screen Wake Lock、外部瀏覽器內 LINE 登入；以三個 LINE 帳號（本人與同學）分別擔任管理員、照護員、督導，走完綁定與督導回覆流程。
- **驗收指標**：輪切分正確率、聲紋自動辨識正確率、意圖準確率、各階段耗時 P50／P95；預取命中率（cache-strategy 第 4 節）。
