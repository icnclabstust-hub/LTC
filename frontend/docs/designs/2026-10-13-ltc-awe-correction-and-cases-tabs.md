## 1. 需求（GD 步驟 1，2026-10-13 提案學生確認）

- **要解決什麼問題**：
  1. 聲紋無法可靠辨識「這是誰」（跨錄音不會被發現的錯誤約 15%），說話人、意圖、句子與輪都可能錯，但沒有地方修正。
  2. 模型都以模擬資料訓練；老師要收集真實場域的修正資料（約 1 萬筆）。
  3. 後端知識庫需要取得確認過的逐字稿。
- **誰會用**：照護員（每輪結束後確認、查看我的案件）；督導（細部修正、人名換代號、最終確認）；後端組（抓取已確認紀錄）。
- **不做會怎樣**：錯誤默默留在資料裡、送給後端；場域上線後收不到可用的訓練資料。
- 決定：
  1. 使用者：照護員＋督導。
  2. 可修正：逐字稿文字、意圖（含需求歸屬）、說話人、句子與輪的邊界。
  3. 說話人改為**每次錄音內匿名 01、02、03**，不長期保存聲紋；照護員把代號對應到角色。
  4. 文字為主；**輪內音訊僅供督導回聽驗證**：存在伺服器、只有督導能播放、督導確認該輪後立即刪除、未確認最長 7 天；不給後端、照護員端不能播放（2026-10-13 提案學生確認）。輪外音訊仍不落地。
  5. 後端**只能取得已確認的紀錄**；紀錄依序編號，後端取走後再保留 30 天。
  6. 人名由督導在確認時**手動換成代號**；有未處理人名的紀錄不能確認。
  7. 新增「我的案件」分頁：照護員查看逐字稿、給督導的問題與回覆。

## 3. 方案比較

### 3.1 修正結果怎麼存

| | 方案 A：每輪一份 JSON 文件（**採用**） | 方案 B：正規化資料表（每句一列、修正欄位） |
|---|---|---|
| 做法 | 新表 `records`：每輪一列，修正後的整輪內容存成 JSON（句子陣列）；系統原始輸出留在 `utterances` | 新表 `corrected_utterances`，每句一列，以外鍵對應原句 |
| 合併／拆句、改輪範圍 | 直接改 JSON 陣列，簡單 | 一句拆兩句、跨輪移動要維護多張表的對應，複雜 |
| 給後端 | 本來就是 JSON，直接輸出 | 要組裝 |
| 查詢統計 | 較不方便（量小，可接受） | 方便 |

### 3.2 後端怎麼取得

| | 方案 A：後端拉取（**採用**） | 方案 B：本服務推送 |
|---|---|---|
| 做法 | `GET /api/export/records?after_seq=N`，後端記住上次取到的編號 | 確認時 POST 給後端 |
| 優點 | 符合「後端抓取」的決定；後端掛掉不影響本服務；不需後端先開端點 | 即時 |
| 缺點 | 有延遲（取決於後端多久抓一次） | 需處理重送、後端端點尚未提供 |

### 3.3 匿名說話人怎麼分

| | 方案 A：錄音中即時分群（**採用**） | 方案 B：每輪結束時整輪重新分群 |
|---|---|---|
| 做法 | 每句整句聲紋與本次錄音的群中心比對（`SpeakerGroups`，0.5），只存在記憶體 | 每輪結束時重算 |
| 結果 | 2026-10-13 評估：以輪為單位分群 F1 0.903 | 0.886～0.895，未較佳 |
| 跨輪一致 | 同一次錄音內，同一人維持同一代號 | 每輪重算，代號可能跳動 |

## 4. 設計

### 4.1 資料模型

```
records（每輪一筆，輪結束時建立）
  seq          INTEGER PRIMARY KEY AUTOINCREMENT   -- 給後端的流水編號
  turn_id, session_id, caregiver_line_user_id, resident_alias
  status       draft | caregiver_checked | confirmed     -- confirmed 才能給後端
  doc          JSON：{ speakers: {"01": "照護員", "02": "長輩"}, sentences: [
                   {start_ms, end_ms, speaker: "01", text, intent, intent_owner, source_idx: [0, 1]} ] }
  has_names    0／1（督導標記「已檢查人名」後才可確認）
  caregiver_checked_at, confirmed_by, confirmed_at, exported_at, created_at, updated_at
```

- `source_idx`：此句由系統原始的哪幾句組成（拆句時兩句指向同一原句），用於訓練資料比對。
- 系統原始輸出（`utterances`）於輪結束 24 小時後照舊刪除；`records.doc` 建立時已複製一份當作修正的起點，並另存 `original` 欄位（系統原始版本，JSON），供訓練比對。

### 4.2 匿名說話人

- `SessionProcessor` 改為：每句整句聲紋 → 本次錄音的 `SpeakerGroups`（門檻 0.5）→ 代號 `01`、`02`…；聲紋只存在記憶體，錄音結束即丟。
- 照護員在確認分頁把代號對應到角色（照護員／家屬／長輩／督導／其他工作人員），同一次錄音內套用到所有該代號的句子；送後端的 `speaker_role` 依此對應。
- 移除：`voiceprints` 表與第一輪建檔流程、`set_speaker` 寫入聲紋。同意流程文字改為「同意錄音，系統會即時區分不同說話人（不保存聲紋）」。

### 4.3 確認／修正分頁

| 身分 | 能做的事 |
|---|---|
| 照護員 | 每輪結束後：把代號對應到角色、改單句說話人、改錯字、改意圖；按「確認」→ `caregiver_checked` |
| 督導 | 看所有照護員的紀錄；除上述外：合併／拆開句子、把句子移到上一輪或下一輪、標出人名並換成代號（例：「王阿姨」→「家屬甲」）；勾選「已檢查人名」後按「確認」→ `confirmed` |

- 拆句：在文字中選擇位置，時間依字數比例估計；督導可回聽該輪音訊確認（第 4.7 節）。
- 人名代號對照表只存在督導的瀏覽器畫面中，不存資料庫、不給後端。

### 4.4 我的案件分頁（照護員）

取代「LINE 案件」分頁，依時間列出本人的：錄音的輪（逐字稿、說話人角色、回答或轉督導狀態、確認狀態）、LIFF 打字提問、LINE 提問、給督導的問題與督導回覆。

### 4.5 給後端：已確認紀錄

```
GET /api/export/records?after_seq=<N>&limit=100
Authorization: Bearer <EXPORT_TOKEN>（.env，不進版控）
→ { records: [ { seq, confirmed_at, resident_alias, speakers, sentences: [...] } ], next_after_seq }
```

- 只回傳 `status = confirmed`；第一次被取走時寫入 `exported_at`。
- 保存期限：未經督導確認的紀錄保存 7 天（P1 實作時改訂，提案學生 2026-10-13 同意；原始 turns／utterances 仍為 24 小時）；已確認紀錄於 `exported_at` 後 30 天刪除；已確認但一直未被取走的，最長保存 90 天（提案學生 2026-10-13 確認）。

### 4.7 督導回聽用音訊

- 錄音中，輪內音訊（`_start_turn` 到 `_end_turn`）邊收邊寫入 `xiaozhao_data/turn_audio/<turn_id>.wav`（16 kHz、16-bit；`xiaozhao_data/` 已排除版控）；輪外音訊照舊不寫入。
- `GET /api/supervisor/turns/{id}/audio`：只有督導（與管理員代督導）能取得；照護員 API 不提供。
- 刪除：督導確認該輪（`confirmed`）時立即刪除；未確認者於輪結束 7 天後由 `cleanup_expired` 刪除。匯出 API 不含音訊。

### 4.6 實作分期

| 期 | 內容 |
|---|---|
| P1 | 匿名說話人（移除長期聲紋）、`records` 資料表、照護員確認分頁（代號→角色、說話人、文字、意圖） |
| P2 | 督導修正（合併／拆句、移輪、人名代號、最終確認）、輪內音訊保存與督導回聽 |
| P3 | 給後端的匯出 API、保存期限 |
| P4 | 我的案件分頁 |

## 5. 安全與隱私

- 文字紀錄保存期限由 24 小時延長（第 4.5 節）；逐字稿可能含健康狀況與人名，人名須由督導換代號才能確認、送出。
- 不保存聲紋；匿名分群只在記憶體。輪內音訊只為督導回聽而保存（第 4.7 節），確認即刪、最長 7 天，不給後端、照護員不能播放；**音訊本身含聲紋特徵，為本功能個資風險最高的部分**。
- 匯出 API 以獨立權杖保護，只給後端組；權杖放 `.env`。
- 模擬資料測試階段：只用同學錄音。**實際場域上線前**：老師核可、機構書面同意、同意書文字更新。

## 6. 測試策略

- 單元：匿名代號在同一錄音內一致、錄音結束後聲紋清除；`records` 建立與狀態流轉；拆句／合併／移輪後 `source_idx` 正確；未勾選「已檢查人名」不能確認；匯出只回傳已確認、`after_seq` 分頁正確、權杖錯誤回 401；保存期限清除。
- 手動：以 tk01～04、sp1～3 模擬錄音走完錄音 → 照護員確認 → 督導確認 → 後端抓取。

## 7. 回滾

匿名說話人與移除聲紋為不可逆的資料變更（舊聲紋會刪除），上線前先備份 `xiaozhao_data/`；其餘功能以分頁與 API 為單位，可個別停用；音訊保存以設定 `KEEP_TURN_AUDIO=0` 關閉。

## 9. 實作紀錄

### 9.1 P1（2026-10-13）：匿名說話人、records、照護員確認分頁

- 說話人：`SessionProcessor` 以整句聲紋、`SpeakerGroups`（0.5）在每次錄音內分出 01、02…；`map_speaker` 讓照護員設定的代號對應在本次錄音中立即生效。移除 `voiceprints` 表（啟動時 `DROP TABLE IF EXISTS`）、聲紋列表／改名／刪除 API、逐句設定說話人 API（改到確認分頁）。`speaker_source` 仍沿用 `'voiceprint'` 表示「自動（聲紋即時分群）」，以免改動既有資料表的 CHECK 條件。
- `records` 表：每輪結束時建立（`services.create_record`），`doc` 與 `original` 為同一份系統輸出；照護員 API：`GET /api/records`、`PATCH /api/records/{seq}`（代號對應、單句角色／文字／意圖／需求歸屬；不能改句子結構）、`POST /api/records/{seq}/check`。代號對應會套用到同一次錄音的其他輪與錄音頁的語句。
- 網頁：照護員新增「確認紀錄」分頁；錄音頁逐句只顯示「說話人 01」與角色；住民管理移除聲紋；同意與使用說明改為「即時區分說話人、不保存聲紋」。
- **與設計的差異（提案學生 2026-10-13 同意）**：設計第 4.5 節寫「未確認紀錄 24 小時刪除」，但督導回聽音訊保存 7 天、督導確認常需超過一天，所以**未經督導確認的 records 保存 7 天**（`RECORD_UNCONFIRMED_TTL_SECONDS`）；原始 `turns`／`utterances` 仍為 24 小時。
- 測試：97 項全過（新增 `test_records.py` 6 項、匿名代號與保存期限各 1 項）。網頁未在瀏覽器實測。
- 遷移：本機資料庫已備份為 `xiaozhao_data/backup-before-anonymous-speakers-2026-10-13.sqlite3`（含 6 筆舊聲紋、9 輪）；以複本驗證啟動遷移可正確刪除 `voiceprints`、建立 `records`，原有資料保留。

### 9.2 P2（2026-10-13）：督導修正、輪內音訊回聽、確認

- 輪內音訊：記憶體只留最近 120 秒，開輪時從輪的起點補寫；一輪結束時只存「輪的起點到最後一句結束」為 `turn_audio/<turn_id>.wav`，結束詞之後、輪外的語音不寫入；沒有句子的輪不存。音訊起點記在紀錄 JSON 的 `audio_start_ms`，網頁逐句回聽時用來跳到對應位置。`KEEP_TURN_AUDIO=0` 可完全關閉。
- 督導 API：`GET /api/supervisor/records`（含 `has_audio`）、`GET /api/supervisor/records/{seq}/audio`、`PUT /api/supervisor/records/{seq}`（整份紀錄，可合併／拆句；伺服器檢查欄位、時間順序、代號、身分、意圖）、`POST .../move`（第一句移到上一輪結尾、最後一句移到下一輪開頭，同一次錄音內）、`POST .../confirm`（須勾「已檢查人名」；確認後鎖定並立即刪除音訊）。
- 網頁：督導新增「紀錄確認」分頁：逐句回聽、代號對應、說話人／身分／意圖／需求歸屬、改字、合併、從游標處拆開、移輪、人名換代號（對照只在畫面，不存檔）。
- 清除：音訊超過 7 天刪除（`cleanup_expired` 依檔案時間）。
- 測試：112 項全過（新增 `test_supervisor_records.py` 15 項）。
- 端對端（真實模型、開發登入、scratch 資料目錄；tk03 125 秒錄音）：4 輪 → 4 筆紀錄與 4 個音訊檔；照護員對應代號與確認、督導回聽（WAV 0.5 MB）、修改、未勾人名被擋、確認後音訊刪除且回 404、照護員呼叫回聽 API 得 403，皆正常。網頁本身未在瀏覽器實測。
- **發現的問題**：tk03 有 3 人，但整次錄音所有句子都被分成同一個代號「01」。服務切出的句子常長達 10 秒以上、一句內混有多人，整句聲紋平均後難以分開（門檻 0.5）。照護員與督導仍可逐句改身分，但代號對應的省力效果有限；需另行評估（例如改用細切片段分群、或提高門檻），屬下一步。

### 9.3 P3（2026-10-13）：給後端的匯出 API、已確認紀錄保存期限

### 9.4 P4（2026-10-13）：我的案件分頁
