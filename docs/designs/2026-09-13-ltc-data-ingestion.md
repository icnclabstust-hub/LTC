# 設計文件：長照資料統一擷取層（法規／據點／SOP 排程同步）

> GD 步驟 3 產出。對應評估表：`docs/designs/2026-09-13-ltc-data-ingestion-assessment.md`（待步驟 4 填寫）。
> 本項為 [2026-09-13-ltc-rag-backend.md](2026-09-13-ltc-rag-backend.md) MVP 設計文件第 9 節已列出的未解決項目（法規排程同步、SOP 文件擷取）的正式開發批次，非 MVP 範圍的自然擴充而非全新專案。

## 1. 背景與問題

依步驟 1 三問確認：

- **要解決什麼問題**：目前三個外部資料源（全國法規資料庫、data.gov.tw 長照據點、衛福部 1966 長照專區 SOP）分別用不同的一次性腳本或即時查詢邏輯擷取，沒有統一排程機制，邏輯重複分散、難以維護。
- **誰會用／多常用**：非人工手動觸發，改為**正式排程自動更新資料庫**，供 RAG 查詢流程持續使用最新資料。
- **不做會怎樣**：法規／SOP 資料停留在「開發時手動跑一次」的狀態，容易過時；核心需求是「所有資訊須符合政府法規效力」，資料不定期同步就可能依據舊法規版本回答，直接違反此硬性要求。

## 2. 目標與非目標

**目標**：

- 三個獨立擷取模組（法規、據點、SOP），各自可排程執行，共用一致的程式風格（日誌格式、錯誤處理模式），不強制共用抽象介面
- SOP 擷取範圍限定 1966 網站「照顧服務相關指引」欄目（`lp-7565-207.html` 列出的項目），含 PDF 文字擷取
- 擷取結果寫入 **PostgreSQL 作為真相來源**（`catalog.documents`／`catalog.chunks`），而非目前 MVP 直接寫 ChromaDB 的做法
- PostgreSQL 寫入後同步更新 ChromaDB，供既有 Naive RAG 查詢使用

**非目標（本次明確不做）**：

- 完整版「惡意內容掃描器」（quarantine + 人工複核佇列）——先做基本文字清理，完整機制留待後續
- 全國法規資料庫擴大到全庫同步——先僅處理長期照顧服務法（沿用 MVP 已驗證的解析邏輯）
- 1966 網站除「照顧服務相關指引」外的其他內容（新聞、一般公告等）
- 即時同步／webhook——採批次排程，非即時觸發
- Elasticsearch／Neo4j 的同步訂閱——這兩庫本身仍是 MVP 設計文件列的第二階段項目，不受本次影響

## 3. 現況與重用

- **全國法規資料庫**：僅提供全庫 ZIP 批次下載，無單一法規查詢 API；MVP 已用網頁版 HTML 解析（`scripts/load_real_law.py`）驗證可行，可重構為排程模組重用其解析邏輯。
- **data.gov.tw 長照據點**：CSV 全量下載＋應用層過濾，已有正式整合（`src/app/integrations/ltc_points_api.py`），目前是「查詢時即時抓取＋記憶體快取 1 小時」，需改為排程寫入 PostgreSQL。
- **1966 長照專區 SOP**：全新調查——列表頁僅 3 筆資料，每筆指向詳細頁，詳細頁僅提供 PDF 下載連結（無網頁全文），**需新開發 PDF 文字擷取**（新依賴，例如 pdfplumber）。

## 4. 方案比較

### 4-1｜排程觸發點

原本比較「WSL2 內 APScheduler」vs「WSL2 內 crontab」，但兩者有共同盲點：**都跑在 WSL2 裡面**。WSL2 預設閒置一段時間或主機睡眠後會被 Windows 關閉，此時無論是 crontab 還是 APScheduler 常駐程序，排定的任務都不會被觸發——這對「正式排程自動更新」是實質風險：資料可能悄悄過時，卻沒有任何錯誤訊息，直接違背我們要解決的核心問題（資料時效性）。真正的關鍵決策點，是排程觸發點該放在 **WSL2 內部** 還是 **Windows 主機層級**：

| | 方案 A：WSL2 內部觸發（crontab 或 APScheduler） | 方案 B：Windows 工作排程器（Task Scheduler）呼叫 `wsl.exe` |
|---|---|---|
| 做法概述 | 三支獨立 Python 腳本，各自用 WSL2 的 `cron` 排程 | Windows 工作排程器定時執行 `wsl.exe -d Ubuntu-22.04 -e python3 ...`，觸發各擷取腳本 |
| 優點 | 純 Linux/程式碼層面設定，簡單、與架構圖「週期性一致性稽核」的排程描述風格一致 | `wsl.exe` 呼叫會自動喚醒/啟動 WSL2 實例，即使原本是關著的，排程時間到一定會執行，不受 WSL2 閒置關閉影響 |
| 缺點／風險 | **WSL2 閒置或主機睡眠時排程不會觸發**，且不會有任何錯誤提示，資料悄悄過時 | 需要在 Windows 端額外設定工作排程器（非純程式碼，部署設定），僅適用於這台機器目前的部署方式；每次喚醒 WSL2 有額外開機延遲 |
| 成本 | 低 | 低（僅需設定，不需新開發） |

**選定方案：B（Windows 工作排程器觸發 `wsl.exe`）**。理由：這是唯一能確保排程真正「正式、自動」執行的做法，直接對應您在步驟 1 提出的「正式排程自動更新資料庫」需求；因為每次都是被喚醒後執行一次就結束，**不需要 APScheduler 常駐程序**，擷取腳本維持簡單的一次性 Python 腳本即可（配合 4-2 的 Outbox 模式，各腳本執行完即結束，不需要維持長連線）。這屬於「部署與運維」層面的設定，記在第 8 節，需要在 Windows 端手動設定工作排程器，非程式碼變更。

### 4-2｜PostgreSQL → ChromaDB 同步機制

| | 方案 A：擷取腳本直接雙寫 | 方案 B：Outbox 模式（PostgreSQL 寫入 + 獨立同步 worker 讀 sync_events 再寫 ChromaDB） |
|---|---|---|
| 做法概述 | 擷取腳本同時寫 PostgreSQL 和 ChromaDB | 擷取腳本只寫 PostgreSQL＋`sync_events` 表；獨立同步任務讀取未處理事件，upsert 到 ChromaDB |
| 優點 | 實作簡單，少一層 | 完全對齊架構圖原始設計；PostgreSQL 是唯一真相來源，未來要接 Elasticsearch／Neo4j 只需訂閱 `sync_events`，不用改擷取邏輯；ChromaDB 寫入失敗可重試而不影響 PostgreSQL 資料完整性 |
| 缺點／風險 | ChromaDB 寫入失敗會讓兩邊資料不一致；未來每加一個檢索庫都要回頭改三支擷取腳本 | 需多寫一個 `sync_events` 表與消費者邏輯，複雜度較高 |
| 成本 | 低 | 中 |

**選定方案：B（Outbox 模式）**。理由：這正是 MVP 設計文件所依附的架構圖原始設計（`sync_events(outbox)` 已在圖上），且第二階段一定會加入 Elasticsearch／Neo4j，現在用方案 A 之後勢必要重構回方案 B；一次做對可以避免技術債。這點與 4-1 的「求簡單」方向不同，因為 4-1 是排程觸發機制的選擇（外部複雜度），4-2 是資料一致性保證的核心設計（沒有捷徑），故在此建議不因求簡化而放棄 outbox 模式。**這裡想請您特別確認**，因為與 4-1 的簡化方向相反。

## 5. 系統設計

**資料流**：

```
Windows 工作排程器（定時）
  → wsl.exe -d Ubuntu-22.04 -e python3 -m ingestion.run --source=<law|ltc_points|sop>
      → 擷取模組（law_crawler / ltc_points_crawler / sop_crawler，各自獨立執行、執行完即結束）
          → 解析內容（HTML / CSV / PDF）
          → 依 content_hash 判斷異動 → 寫入 catalog.documents / catalog.chunks
          → 寫入 catalog.sync_events（operation: upsert/soft_delete）
Windows 工作排程器（另一個定時任務，頻率可與擷取不同）
  → wsl.exe -d Ubuntu-22.04 -e python3 -m ingestion.sync_worker
      → 讀取未處理 sync_events → upsert 到 ChromaDB → 標記 event 已處理
```

**對外介面**：無新增 API port（背景排程服務）；CLI 入口如 `python -m ingestion.run --source=law`，供 Windows 工作排程器透過 `wsl.exe` 呼叫，也可在 WSL2 內手動執行測試。

**資料模型／schema 變更**：

- 沿用 `db/models.py` 的 `Document`／`Chunk`
- 新增 `catalog.sync_events(event_id, doc_id, operation, payload, created_at, processed_at)`

**錯誤處理與日誌**：

- 單一來源擷取失敗不應擋住其他來源（各腳本獨立執行、獨立排程）
- PDF 解析失敗記錄錯誤並跳過該筆，不中斷整批
- 三支擷取腳本共用一致的 log 格式（來源名稱、筆數、成功/失敗、耗時）

## 6. 安全與隱私考量

- PDF／HTML 內容寫入前做基本文字清理（移除潛在注入樣式、隱藏字元），對應架構圖「惡意內容掃描器」的簡化版；完整 quarantine／人工複核機制留待後續
- 三個來源均為政府公開資料，無個資疑慮
- `CODE_REVIEW_STANDARD.md` 表 B／D／E 完整內容仍未取得，待補齊後對照

## 7. 測試策略

- **單元測試**：PDF 解析、HTML 解析邏輯（現有 `load_real_law.py` 解析可重構出可測試函式）、content_hash 異動判斷
- **整合測試**：mock 外部 HTTP 呼叫，測試排程流程端對端（擷取→PostgreSQL→sync_events→ChromaDB）
- **驗收測試**：排程跑一次後，PostgreSQL／ChromaDB 資料筆數符合預期，且 SOP PDF 內容可被正確檢索

## 8. 部署與運維

- **不使用 WSL2 內部 crontab**，改在 Windows 端設定「工作排程器」（Task Scheduler），動作設為執行 `wsl.exe -d Ubuntu-22.04 -e python3 -m ingestion.run --source=<來源>`，觸發程式為 `wsl.exe`（非直接排程 Python 腳本），這是部署設定而非程式碼
- 三個擷取來源＋一個 sync_worker，共建立 4 個 Windows 工作排程器任務，各自獨立設定觸發頻率（見第 9 節，頻率尚待決定）
- 不使用 Docker，延續既有偏好
- 監控：MVP 階段先以日誌為主，正式 `eval.alerts` 機制留待召回率量測模組建立後串接；另建議工作排程器啟用「上次執行結果」通知，方便肉眼確認排程是否正常跑
- 回滾：`sync_events` 保留歷史記錄可重放；PostgreSQL 用 migration 版本控制（仍是未解決項目，見下）

## 10. 現況調查補充（2026-10-12）：1966 網站其他「服務項目」子欄目 + 長照3.0現行度

**調查動機**：既有 SOP 擷取範圍限定於「照顧服務相關指引」（第 4 節非目標已排除「其他內容」），但該欄目另有 7 個同層級「服務項目」子欄目（給付及支付、家庭照顧者支持服務、失智照護、住宿式機構服務、醫療銜接長照、社區整體照顧服務體系、聘僱外看家庭可使用長照服務）未曾檢視是否也有可擷取的結構化 SOP 文件，故臨時調查，結論記錄於此、不另開設計文件。

**調查結論**：

- 上述 7 個子欄目多為「清單頁 → 政策公告/補助方案/評鑑基準」，非操作型 SOP，不建議擴充 `sop_crawler.py` 收錄。
- 唯一例外：「社區整體照顧服務體系」頁面下的「長照專業服務手冊」及其操作指引系列（共 12 份 PDF，公告日 112-01-09）在文件型態上符合現有 SOP 擷取模式。

**但發現更高優先的風險（長照3.0現行度）**：

- 查證長照3.0 自 2025-09-01 起分階段上路（第二階段 2026-01-01、輔具租賃新制 2026-07-01）。
- 現有 4 部法規語料（含本次擴充的 3 部子法）因 `law_crawler.py` 即時抓取政府網站現行版本，**已自動反映 3.0 修正條款**（已查證「長期照顧服務申請及給付辦法」修正日 114-06-19，條文本身即含 115 年分階段施行內容），無需額外處理。
- 既有 3 份 SOP（翻身拍背、肢體關節活動、督導員工作手冊）為純照護技術操作，不涉給付代碼，不受 3.0 影響。
- 但上述新發現的「長照專業服務手冊」（112年／長照2.0時期公告）**是靜態公告文件，不會隨法規修正自動更新**；搜尋未找到 115 年新版公告，而其上層法規已修正並分階段施行，故手冊內服務代碼／給付次數等操作細節有與現行規定脫節的風險。

**決定**（經使用者確認）：**暫不收錄**「長照專業服務手冊」系列 12 份 PDF，標記待查——待衛福部發布 3.0 版手冊，或有能力人工比對新舊差異後再評估收錄。其餘 7 個子欄目維持不擴充。
