# 設計文件：Advanced RAG 技術升級（切分／混合檢索排序／查詢改寫／評測指標）

> GD 步驟 3 產出。對應評估表：`docs/designs/2026-09-13-ltc-advanced-rag-assessment.md`（待步驟 4 填寫）。
> 這是課程規定的技術規格，範圍超出 MVP 設計文件明確定義的「非目標」（進階排序、混合檢索原本列為第二階段），視為新開發批次。

## 1. 背景與問題

依步驟 1 確認：

- **要解決什麼問題**：課程規定的技術規格要求，同時要解決現行系統召回率與答案準確性不足的問題（MVP 端對端測試已發現：相似度門檻校準不足、簡單重疊率忠實度檢查不夠精確）。
- **誰會用**：同一套系統的照護員使用者，這批是技術架構升級，不改變使用者操作方式。
- **不做會怎樣**：不符合課程技術規格要求；召回率與準確性問題持續無法系統性改善。

## 2. 目標與非目標

**目標**：

1. **切分（chunking）改用 NLP 句法切分**：以中文句子邊界（非單純段落/字數硬切）為單位分組成 chunk，避免現行 `sop_crawler.py` 的固定字數切分在語意中斷處硬切
2. **混合檢索與排序改用 LambdaMART**：在既有 ChromaDB 向量檢索之外新增 BM25 稀疏檢索，兩者以 RRF 融合（補上架構圖原本設計、MVP 尚未實作的融合節點），融合後的候選集合交給 LambdaMART 模型重新排序
3. **查詢改寫需做相似度回檢**：查詢前處理新增改寫步驟，改寫後與原查詢計算相似度，過低則捨棄改寫結果、改用原查詢
4. **新增評測指標**：Context Recall、Faithfulness（量化版，非現行二元判定）、首輪解決率，寫入既有 `eval` schema

**非目標（本次明確不做）**：

- LambdaMART **模型訓練**本身——目前 `eval.golden_queries` 沒有標註資料，依步驟 1 您確認「之後會做測試」，本次先建好特徵萃取與訓練 pipeline，模型先以既有相似度排序作為 fallback，待累積標註資料後再訓練
- Elasticsearch 正式導入——用輕量的 `rank_bm25`（純 Python，讀 ChromaDB 現有文字內容建索引）做稀疏檢索，不引入新的資料庫服務，避免違反 MVP 已定案的「不用 Docker、控制資源用量」原則
- Neo4j 圖譜檢索——仍不在本次範圍

## 3. 現況與重用

- 現行切分：`law_crawler.py` 以法規條文為天然單位（無需改動，已符合語意邊界）；`sop_crawler.py` 目前是固定 1500 字硬切（`_split_into_chunks`），這是本次要換掉的部分
- 現行排序：`Reranker`（`app/core/rerank.py`）目前只是依相似度排序的 passthrough，docstring 本來就預留「之後可替換 rerank() 內部實作」的擴充點，可直接在此擴充
- 現行忠實度：`check_faithfulness`（bigram 重疊率）可保留作為線上即時判定（低延遲需求），評測用的 Faithfulness 指標另外做量化版本，不影響線上路徑效能
- 已確認本機無 `lightgbm`、`rank_bm25`，需新增依賴

## 4. 方案比較

### 4-1｜中文句子切分方式

| | 方案 A：規則式標點切句 | 方案 B：NLP 模型（spaCy／HanLP 中文管線） |
|---|---|---|
| 做法概述 | 用正規表示式依 。！？；等標點加引號配對規則切句，再依字數上限分組成 chunk | 載入中文 NLP 模型做斷句（含更準確的縮寫/引號/巢狀標點處理） |
| 優點 | 輕量、無新增大型依賴、速度快 | 斷句準確度理論上更高 |
| 缺點／風險 | 遇到複雜巢狀標點可能偶有誤切 | 需額外安裝數百 MB 模型，這台機器資源已經偏緊繃（先前 Elasticsearch 曾因記憶體壓力重啟過） |
| 成本 | 低 | 中高 |

**選定方案：A（規則式標點切句）**。理由：法規與 SOP 文件的標點使用相對規範（不是社群媒體那種高噪音文本），規則式切句已能達到良好準確度；且延續本 repo 目前的資源節制原則。若日後發現切句品質不足，可再評估換成方案 B。

### 4-2｜混合檢索融合方式

| | 方案 A：ChromaDB 向量檢索 + BM25 稀疏檢索，RRF 融合 | 方案 B：導入 Elasticsearch 做稀疏檢索 |
|---|---|---|
| 做法概述 | 用 `rank_bm25`（純 Python）對 ChromaDB 裡的文字內容建 BM25 索引，與向量檢索結果做 RRF 融合 | 用已裝好但 MVP 未串接的 Elasticsearch 做全文檢索，取代 rank_bm25 |
| 優點 | 不新增資料庫服務、不用維護額外索引同步機制，補上架構圖 RRF 融合節點 | Elasticsearch 全文檢索能力更完整（中文分詞、更多查詢語法） |
| 缺點／風險 | BM25 索引需在記憶體中重建（文件量大時效能需留意，目前僅 72+3 份文件規模無虞） | 需要額外設計 PostgreSQL→Elasticsearch 的 outbox 訂閱同步（這是 MVP 明確列為第二階段的項目），且先前實測 Elasticsearch 記憶體壓力大 |
| 成本 | 低 | 高（等於提前做第二階段的 Elasticsearch 整合） |

**選定方案：A**。理由：現階段文件規模小，`rank_bm25` 完全夠用且不新增服務依賴；Elasticsearch 整合本來就排在 MVP 設計文件的第二階段，這次順便做等於範圍蔓延，不符合「先判斷再開發」精神。

### 4-3｜LambdaMART 實作方式

| | 方案 A：LightGBM `LGBMRanker`（objective=lambdarank） | 方案 B：自行實作 LambdaMART 演算法 |
|---|---|---|
| 做法概述 | 用 LightGBM 現成的 lambdarank 目標函數訓練排序模型 | 從論文自行實作梯度計算與訓練迴圈 |
| 優點 | 業界標準實作、穩定、有完整文件；訓練/推論介面單純 | 完全掌控細節 |
| 缺點／風險 | 需新增 `lightgbm` 依賴（純 CPU 版不大） | 開發與除錯成本高、容易有數值誤差，沒有對應的學習效益（課程規定的是用 LambdaMART 這個方法，不是要求重造輪子） |
| 成本 | 低 | 高 |

**選定方案：A**。理由：課程規定使用 LambdaMART 演算法本身，用業界標準函式庫實作即符合要求，重新造輪子的風險與成本不合理。

## 5. 系統設計

**資料流（更新後的查詢路徑）**：

```
照護員提問
  → 查詢改寫（Ollama 生成改寫版本）→ 與原查詢算相似度 → 過低則捨棄改寫，使用原查詢
  → 意圖辨識（沿用現有 intent.py）
  → 法規/SOP 查詢：
      ChromaDB 向量檢索 ─┐
                          ├→ RRF 融合 → LambdaMART 重排序（無訓練模型時 fallback 為現行相似度排序）
      BM25 稀疏檢索      ─┘
      → 證據判定 → 忠實度守門員（線上即時，沿用現行 bigram 版）→ Ollama 生成 → 回應
```

**對外介面**：無新增 API port，`/api/query` 內部流程更新；新增離線指令：

- `python -m eval.train_ranker`：讀取 `eval.golden_queries` 訓練 LambdaMART 模型（目前資料為空時應提示並略過，不報錯中斷）
- `python -m eval.run_metrics`：跑 Context Recall／Faithfulness／首輪解決率，寫入 `eval` schema

**資料模型／schema 變更**：

- 新增 `eval.metric_runs`（`run_id`, `metric_name`, `value`, `query_id` 外鍵, `created_at`）
- `LambdaMART` 模型檔案存本機路徑（非資料庫），路徑經 `.env` 設定

**錯誤處理與日誌**：

- LambdaMART 無訓練模型時，reranker 自動 fallback 為現行相似度排序，記錄一次性警告（避免每次查詢都洗版日誌）
- 查詢改寫呼叫 Ollama 失敗時，直接使用原查詢，不阻斷主流程

## 6. 安全與隱私考量

- 訓練資料來自照護員回饋（`eval.feedback_sync`）與人工標註（`eval.golden_queries`），已有既有的去識別化考量（見回饋迴圈設計文件第 6 節），本次沿用
- BM25 索引僅存於記憶體/本機，內容為政府公開法規/SOP 文字，無新增隱私風險

## 7. 測試策略

- **單元測試**：中文切句函式（含引號/標點邊界案例）、RRF 融合邏輯、LambdaMART fallback 行為（無模型時是否正確退回相似度排序）、查詢改寫相似度回檢邏輯
- **整合測試**：端對端跑一次含 BM25+向量混合檢索的查詢，確認排序結果合理
- **驗收測試**：`eval.run_metrics` 在有 golden_queries 資料時能正確算出三項指標（目前資料為空，先用少量人工造的測試資料驗證計算邏輯正確）

## 8. 部署與運維

- 沿用 WSL2 原生＋不使用 Docker
- 新增依賴僅 `lightgbm`、`rank_bm25`，皆為純函式庫，不需額外服務
- LambdaMART 訓練與評測指令為手動/未來排程執行，本次不強制排入 Windows 工作排程器（等有真實標註資料後再排程）

## 9. 未解決問題

- LambdaMART 排序特徵集尚未定案（初版先用：向量相似度、BM25 分數、chunk 長度、是否命中查詢關鍵字），實際訓練後可能需要調整
- 首輪解決率的精確定義需要再确認：暫定為「查詢在未經改寫回退、且忠實度守門員一次通過、且證據判定為足夠」的比例，如果理解有誤需要調整
- Context Recall／Faithfulness 量化版的計算方式需要在 golden_queries 有真實資料後驗證是否合理
- 中文句子切分的正規表示式規則需要用實際法規/SOP 文本多跑幾個邊界案例確認穩健度

## 10. 現行系統（Naive RAG）基準測試（2026-10-12）

**目的**：在決定是否啟動本批升級前，先量化現行 Naive RAG（純向量檢索＋排序 passthrough）的實際表現，作為之後比較的基準。測試對象為現行 `/api/query` 端點，共 12 題，涵蓋 4 部法規／3 份 SOP／長照據點／邊界案例（證據不足、模糊、身份問題、真正離題）。

| # | 類別 | 查詢 | 耗時 | 結果評估 |
|---|---|---|---|---|
| 1 | 法規-機構評鑑 | 長照機構評鑑是誰負責？ | 33.5s | 引用正確（長服法第39/7條），但答案混入不相關的督導員手冊段落 |
| 2 | 法規-施行細則 | 對長照人員資格的規定？ | 11.2s | 正確、乾淨 |
| 3 | 法規-給付辦法 | 申請及給付的規定？ | 20ms | 命中 Redis 快取（與先前驗證查詢完全相同字串） |
| 4 | 法規-訓練認證 | 繼續教育及登錄？ | 15.0s | 正確、高信心 |
| 5 | SOP-翻身拍背 | 注意什麼？ | 22.3s | 幾乎整段PDF原文堆砌，非精簡答案 |
| 6 | SOP-肢體關節 | 操作方式？ | 20.0s | 結構清楚、高信心 |
| 7 | SOP-督導員 | 工作內容？ | 15.0s | 結構清楚、高信心 |
| 8 | 長照據點 | 台南市有哪些據點？ | 0.5s | **Bug：問台南市，回傳高雄市據點** |
| 9 | 邊界-3.0輔具 | 輔具全租賃申請？ | 11.7s | 法規本身已含3.0輔具條款（非bug），但夾雜不相關的契約條款段落 |
| 10 | 邊界-模糊 | 評鑑與補助流程關聯？ | 9.1s | 答案東拼西湊，混入不相關的認可法人課程認定內容 |
| 11 | 身份問題 | 你是誰？ | 2.4s | **Bug：沒有觸發人設「我是小照」，被證據判定擋成拒答** |
| 12 | 真正離題 | 明天天氣如何？ | 2.6s | 正確拒答 |

**延遲**：生成路徑（含Ollama呼叫）9.1s–33.5s，平均約17.3s；證據不足/離題短路路徑（不呼叫生成）2.4–2.6s；快取命中20ms。

**發現的既有程式缺陷（非本批升級範圍，獨立問題）**：
1. `query_ltc_points` 城市過濾邏輯失效：查台南市回傳高雄市據點。
2. 身份類問題（如「你是誰？」）被 `evidence.py` 證據判定機制擋在生成之前判為 INSUFFICIENT，導致 `generation.py` 系統提示詞裡設計的「簡短回答你是小照」人設邏輯從未被觸發。

**對本批升級決策的參考**：第5、9、10題顯示的「檢索到不相關片段混入答案」問題，與本文件第1節背景描述的「召回率與答案準確性不足」現況相符，為 Hybrid 檢索＋重排序的實際改善目標提供了具體基準案例（可作為日後比較 A/B 的案例，若之後訓練 LambdaMART 也可作候選標註資料）。
