## 二、問題定義（三問）

1. **要解決什麼問題**：現行（規劃中）RAG 架構存在多資料庫不一致、無法量測召回率、生成內容缺乏忠實度把關、回傳資料正確性不足；需為長照照護員提供可溯源、符合衛福部規範與政府法律效力的長照法規／SOP 回應。
2. **誰會用？多常用？**：長照照護員，查詢長照 3.0 相關法規與操作流程 SOP。本階段部署範圍為本地／實驗室內部 demo。
3. **不做會怎樣？**：照護員可能取得未經來源佐證、已失效或錯誤的法規／SOP 資訊，若依此執行照護行為，有違反衛福部規範或延誤正確處置的風險。

## 八之一、探索性 Spike 登記（2026-09-13 追加）

- 範圍：驗證 ChromaDB、Elasticsearch、Neo4j、Redis、Open WebUI、PostgreSQL 六項服務能否於本機原生安裝並成功啟動、互相連通（連線層級的 smoke test），**不包含**開發 Neo4j 圖譜查詢或 Elasticsearch 全文檢索功能本身——這兩項功能仍維持設計文件第 2 節「非目標」，留待第二階段正式設計。
- 時限：本次會談範圍內完成，若逾期或需要正式功能開發，須回頭補正式設計文件段落。
- 事由：確認本機環境（是否有 WSL2／各服務可否原生安裝）是否足以支撐未來第二階段擴充，降低後續設計的不確定性。
- **結果（2026-09-13 完成）**：六項服務全數連通成功。
  - Redis、ChromaDB（內嵌模式）：開箱即用
  - Neo4j：預設帳密已過期，改為本機開發密碼後驗證成功
  - PostgreSQL：機器上已預先安裝並啟動服務，但無應用程式角色，由學生執行 `createuser`/`createdb`/`ALTER DATABASE` 後連通成功
  - Elasticsearch：預設啟用安全機制（HTTPS＋帳密），由學生執行 `elasticsearch-reset-password` 後連通成功；測試過程中觀察到 ES 曾因記憶體壓力自動重啟一次（尖峰約 8.4GB），第二階段若要正式使用 ES，需評估 WSL2 記憶體配置（`.wslconfig`）
  - Open WebUI：無 Docker，改用 `pip install --user open-webui`（需 python3.11，系統預設 python3.10 不相容），啟動後 `/health` 回應正常
  - 額外發現：本機（WSL2 Ubuntu 22.04）已預先安裝 PostgreSQL／Redis／Elasticsearch／Neo4j／Ollama 並設為開機啟動，與 git repo 內容（僅治理文件）不同，這點補充了步驟 2 現況調查的機器層級發現
  - 過程中密碼曾一度直接貼在對話中，已提醒學生日後密碼類資訊改用本機檔案傳遞，不進對話紀錄
